# 群屿 Qunyu 0.4

Windows 本地运行的 QQ 群友与助手。0.4 增加可选MCP扩展工具、逐次审批与执行回执，并补强工具执行前的撤权和来源检查。保留模型分工、接话规划、表达学习、长对话摘要，以及 NapCat、SnowLuma、QQ 官方机器人接入。机制参考见 [官方资料对照](docs/RESEARCH-v0.3.md)，代码独立实现。

## 解压使用

1. 解压 `Qunyu-0.4.0-Windows-x64.zip`，保留整个 `Qunyu` 文件夹。
2. 双击 `Qunyu.exe`，从自动打开的浏览器进入管理台。发行包内置运行环境，不需要安装 Python、Node 或数据库。
3. 填写兼容 Chat Completions 的模型地址、模型名和密钥，测试后保存。支持本地兼容模型服务。
4. 先在本地试玩，再选择 QQ 接入方式、设置主人与群允许列表。

聊天质量由所选模型决定。项目没有内置收费模型、免费额度或演示 AI 回复。无模型时，本地管理、显式记忆、词典、待办、明确提醒、计算及词法知识检索仍可用。

## 0.4 扩展工具与执行回执

原有记事、检索、提醒不需要MCP。需要接入自己部署的笔记、日程等服务时：

1. 在“扩展工具”添加服务地址和可选Bearer Token，点击“发现工具（联网）”。发现不会执行工具。
2. 选择允许的工具、保存名单并启用服务。在当前会话开启“允许提出扩展工具请求”，同时保留工具总开关。
3. 在聊天中提出请求；模型若选择扩展工具，只创建待批准操作。管理台展示服务、参数和真实来源。
4. 检查后逐次批准。结果仅在本地记录展示；在QQ中追问时，模型可查询当前请求人的有效执行回执，不主动推送结果。

支持MCP 2025-11-25／2025-06-18／2025-03-26的Streamable HTTP握手、工具目录与调用，兼容该传输中的JSON或有界SSE响应；不支持旧的独立SSE传输、stdio进程、OAuth、异步tasks、采样和询问客户端。远程只允许公网HTTPS，本机可用HTTP，不连接局域网／云元数据地址，不自动跟随重定向或代理。

最多8个服务、每个目录50个工具、每轮模型最多16个扩展工具，目录缓存15分钟，重启后需重新发现。参数定义上限12KB／12层，暂不支持引用或正则Schema；不支持的定义会过滤。批准前重新发现并核对定义指纹，原参数不可在审批接口替换。

待批准10分钟有效；配置、权限、来源、记忆版本或请求变化后不能沿用。所有MCP调用需逐次批准；断线／超时标记结果未知，不自动重试。停止等待不能撤回已发送的外部操作，须在目标服务核对。

内置模型工具也记录实际结果，即使后续模型答复失败仍可查看。工具参数按定义校验、结果有界注入；QQ撤权、停用连接、清除来源后在执行入口拦截。发现及工具执行不计入模型Token预算，第三方服务可能自行收费。

执行记录在本地 `data/tool_runs.json`，保留最近最多200条并受空间上限约束；待批准和执行中记录在重启后分别取消／标记未知，不自动恢复操作。记录不进入数据库备份；复制完整data可保留。数据库恢复会取消待审批，历史执行记录不随旧快照重放。MCP令牌DPAPI保护，网页和备份不回显，恢复后清除并停用服务。

## 0.3 保留的能力

| 能力 | 实际行为 |
| --- | --- |
| 模型池与任务路由 | 可为聊天、记忆与语言学习、接话判断、摘要、Embedding 分别指定模型；不指定仍使用原默认配置 |
| 明确的备用模型 | 最多3个按序备用，仅在建连失败、限流和服务端故障时尝试；鉴权、配置、预算或响应超时不换服务；连续暂时故障冷却30秒 |
| 接话规划 | 根据直接请求、话题、参与者、冷却和近期回答决定 reply/wait/skip；可在会话页查看实际原因 |
| 请求打断 | 同一成员的新明确请求或停止消息能阻止旧回复发送及尚未开始的工具；已执行结果保留真实记录 |
| 独立表达学习 | 从至少3条、2位成员的真实用例生成短表达候选，审核和采用分别控制；不混入黑话词义 |
| 长对话摘要 | 旧对话按人物、话题、约定和未完成事项整理；保留近期原文，摘要保留来源指纹与依赖版本，删除或更正来源后失效 |
| 本地自检 | 显示模型路由、熔断、QQ允许列表、预算、候选和摘要状态；不自动联网，不把配置就绪当作连接成功 |

只用一个模型时，继续在“默认模型”填写原有三项即可。需要分工时，在“模型池”添加配置并保存任务分工。备用服务会接收相同相关上下文，只有明确选中的备用配置才会被尝试。

自动长对话摘要需要“设置与连接”的全局开关，以及“群与会话”的单会话开关同时开启。默认超过60条或18000字触发，保留最近24条并尽量保持完整轮次；单次整理输入有上限，失败保留当前有效原文。“知识与检索”可手动整理，不受自动开关限制，但仍检查暂停、会话权限与预算。摘要不是精确事实库，可能遗漏细节。

表达学习和采用默认关闭；“群语言与表达”里分别管理词义与措辞。自动表达必须有多人用例和来源，始终待审核；手动教授的表达可以直接选审核状态。只有会话允许采用且单条已审核、允许使用的短语才进入风格资料，不冒用群友身份。

| 可选语义检索 | 真实 `/embeddings` 接口与词法排名结合，独立缓存，费用计入同一预算；失败明确降级 |
| 文档知识 | TXT、MD、CSV、JSON、PDF、DOCX，8MB／30万字上限；分段检索而非整篇注入聊天 |

| 连续消息 | 同一群同一成员的短消息合并，最多8条／3张图；每群最多8个在途回复任务 |
| 自动黑话候选 | 多人多次用例或明确解释才进入分析，保留来源与例句，生成结果必须审核 |
| 黑话多义 | 根据话题与例句重排含义，保留歧义；学习、理解、主动使用分别控制 |
| 办事增强 | 批量待办、确认完成、明确提醒改期，以及通过聊天更正或删除自己的记忆 |
| 来源失效 | 多轮复述继承来源和版本，派生事实依赖失效后不能继续召回；旧来源不能绕过删除重建 |

在“知识与检索”中可直接检验问题能找到哪些片段，无需先产生模型回复。人物画像与检索同样按会话和用户可见范围过滤。

## 记忆如何使用

```text
记住：我住上海
记住：我现在住杭州
我的记忆
更正记忆：记忆ID → 我住苏州
删除记忆：记忆ID
我们群里“开饭”指一起打游戏
解释黑话：开饭
```

自动整理默认先审后用。在知识页可手动整理指定用户的近期消息；需要至少4条有效原始用户消息、开启自动记忆，并使用已配置模型。是否值得记住、提取置信度与黑话词义都可能判断错误，须检查来源。

冲突依据是同一会话、用户、对象和属性。居住城市、生日与偏好称呼只做保守规则识别，其他事实可以填写可选属性键；这不是完整的语义矛盾推理。多人关系、玩笑、第三人转述不会被规则当作自己的居住地。

删除记忆会阻断它及相关旧来源参与检索和模型上下文；原始聊天、历史备份仍须单独清理。旧备份恢复等于恢复过去的快照，请检查后再启用。

## 资料与语义检索

知识页支持文件导入、以指定用户身份检索、查看命中片段与来源。相同原文件在同一会话重复导入会去重。PDF依赖文字层，不支持扫描件OCR；DOCX提取正文与表格文字，不提取图片、批注或复杂版式。单份PDF最多300页。

语义检索默认关闭。可在任务分工里选择专用配置，使用该配置的模型名、服务地址、密钥和输入价格；不指定路由时，填写独立的 Embedding 模型名及价格，并使用默认服务地址与密钥。服务须提供兼容 `/embeddings` 接口；聊天模型名称不等于 Embedding 模型名称。

每次查询只新增最多12个预选片段向量，每份长文件最多3个；已缓存且当前仍获授权的片段参与语义排名。大库冷启动时可能遗漏没有词法线索的内容。向量与门控请求共享Token／费用预算；统计与账单仍以服务商为准。语义服务出错时会返回降级诊断。

兼容向量请求格式核对自 [OpenAI Docs：Create embeddings](https://developers.openai.com/api/reference/resources/embeddings/methods/create)。

## 群聊与黑话

默认均衡模式，优先处理被提及、叫名或真实回复自己的消息。活跃模式可参与开放问题；额外语义门控默认关闭，开启后只对候选场景限频判断并计入用量。不要把门控当作能准确理解所有群聊话题的保证。

在“群与会话”设置别名、合并窗口、冷却、后续交流窗口、安静时段、会话预算和工具权限。每群默认20秒非直接接话冷却，合并窗口600毫秒。直接提及仍可处理；持续高频消息超过队列上限只观察，不继续增长回复队列。

黑话学习默认关闭。开启后，观察到足够证据才批次调用模型，也可手动分析。新词义总是待审核；关闭学习后不再产生候选，关闭理解后不自动召回，主动使用还需会话开关与单条词条开关同时允许。规则和模型不保证所有用例都属于黑话。

## 待办与提醒

```text
添加待办：检查资料
完成待办：检查资料
添加待办：
1. 整理报名名单
2. 准备发布说明
5分钟后提醒我喝水
明晚八点提醒我交作业
把喝水提醒改到后天晚上九点
每天晚上9点提醒我喝水
我的待办
取消任务：任务ID
计算：(12+8)*3
总结最近聊天
```

时间按UTC+8解释。提醒需要电脑与群屿运行、对应通道在线；睡眠和关机无法准点送达。未知送达结果保留失败状态，需要核对后手动重试。当前支持一次性、每日和每周，复杂周期与共享日历仍未实现。

## QQ接入

### NapCat / SnowLuma

先独立部署协议端、完成QQ登录，并启用同时提供消息事件与动作的 OneBot v11 Universal WebSocket。

- 正向：在群屿填写 `ws://127.0.0.1:端口/...`，使用独立 Access Token 字段，填写主人QQ号与允许群号。
- 反向：群屿不填正向地址，在协议端填写 `ws://127.0.0.1:群屿端口/onebot/v11/ws`，两端连接密钥一致。
- 默认端口8765，被占用时选择后续端口，以浏览器地址为准。连接密钥至少12位。
- 默认只处理允许列表群和主人私聊；群中来自不同成员的消息不会合并成同一人的授权。

[NapCat文档](https://napneko.github.io/guide/boot/Shell) · [SnowLuma文档](https://snowluma.github.io/en/docs/guide/introduction)

### QQ官方机器人

填写AppID/AppSecret与群／用户OpenID允许列表，使用官方 `qq-botpy` SDK。OpenID不同于普通QQ号码；初次接收但未放行的对象可在事件中查看。被动回复关联原消息，主动提醒受平台权限与额度限制。

官方机器人能接收的群消息由腾讯权限及事件支持决定，不能承诺具有协议端相同的全群旁听能力。本版不包括频道接入。具体资格、网关方式、审核和主动发送额度以开放平台为准。

[腾讯官方Python SDK](https://github.com/tencent-connect/botpy)

## 本地运行、备份与升级

关闭浏览器不会退出服务；托盘或管理台可退出。开机启动默认关闭，可在设置显式开启。程序只绑定本机回环地址。

便携数据在EXE同级 `data` 目录。Windows密钥使用当前账户DPAPI保护，换用户或机器须重新填写。`data/admin.token` 是本机管理凭据，启动器通过链接建立会话后会清除地址凭据；不要分享该文件或含凭据的启动链接。

备份包含主数据库与脱敏配置，不含默认／命名模型、QQ与MCP密钥、管理凭据、向量缓存或独立工具执行记录。恢复前建立安全副本；恢复后暂停、清除密钥并关闭连接，检查后再启用。0.4沿用schema 1，可恢复0.1—0.3备份。

升级建议：先在旧版下载备份并退出；把新版解压到新文件夹。可在同一Windows用户下把旧版整个 `data` 目录复制到新版EXE旁，或在新版恢复备份。保留旧目录作为回退，不要只复制EXE。构建输出按版本隔离，遇到输出目录已有用户数据会拒绝覆盖。

## 开发与测试

Python 3.12：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-dev.txt
.\.venv\Scripts\python.exe -m qunyu
.\.venv\Scripts\python.exe -m pytest -q
powershell -File scripts/build.ps1
```

可用 `--data-dir`、`--port`、`--no-browser`、`--no-tray`。冻结包在 `dist/v0.4.0/Qunyu`，ZIP在 `dist/`。锁定依赖见 `requirements-lock.txt`，接口补充见 `qunyu/static/INTEGRATION-v0.4.md`。

测试使用替身模型、模拟QQ和自建来源，不联系真实账号。DPAPI验收需要正常Windows用户环境。实际检查记录见 `TEST_REPORT.md`；限制见 `RELEASE_NOTES.md`。
